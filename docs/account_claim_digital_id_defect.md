# Backend Contract Defect: Account Claim Digital ID Regex

**Status:** BACKEND CONTRACT DEFECT (not fixed in this task — backend read-only)

## Conflict

| Layer | Behavior |
|---|---|
| `patients/services.py` | `generate_digital_id()` returns `f"PT-{'-'.join(groups)}"` → `PT-XXXX-XXXX-XXXX` (canonical Digital ID) |
| `claims/serializers.py` | `AccountClaimSubmissionSerializer.digital_id = serializers.RegexField(r"^\d{17}$")` → requires exactly 17 digits, no `PT`, no hyphens |

A real Digital ID generated by the same backend (`PT-XXXX-XXXX-XXXX`) **cannot** satisfy the account-claim serializer.

## Impact

- `POST /account-claims/` rejects every canonical Digital ID with `validation_error`.
- End-to-end claim submission **cannot PASS** until the backend serializer accepts the canonical format.
- Flutter must NOT compensate: no stripping of `PT`, no hyphen removal, no hashing/transforming the Digital ID.

## Flutter stance

- Models and displays the canonical format `PT-XXXX-XXXX-XXXX`.
- Claim form accepts the real Digital ID as typed by the owner.
- Claim submission is reported as **BLOCKED by backend regex**, not verified end-to-end.

## Reproduction evidence

- Backend SHA: `edb3969`
- `patients/services.py` line ~20: `return f"PT-{'-'.join(groups)}"`
- `claims/serializers.py`: `digital_id = serializers.RegexField(r"^\d{17}$")`

## Resolution (backend-side, out of scope here)

Allow the canonical `PT-XXXX-XXXX-XXXX` pattern (e.g. `^PT-[A-Z0-9]{4}-[A-Z0-9]{4}-[A-Z0-9]{4}$`) or normalize before validation.
